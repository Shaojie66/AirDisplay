# M4 打磨

## b. 自动化（2026-10-24）

| 场景 | 行为 |
|---|---|
| Sender 启动 | 只监听，不建虚拟屏 |
| Air 连上 | 自动建虚拟屏并开始推流 |
| Air 断开（拔线、退出 Receiver） | 等 3 秒，还没连回来就移除虚拟屏，窗口回到 Pro 主屏 |
| Air 重新连上 | 虚拟屏重新出现，推流恢复 |
| Receiver 没连上时 | 只显示一个普通小窗口（不全屏），系统的权限弹窗不会被挡住 |
| Receiver 连上 | 自动切成无边框全屏 |
| Receiver 断线 | 3 秒后退回小窗口，Air 恢复正常桌面；连回来后自动回到全屏 |

- 开关：Sender 控制面板「Air 断开时移除虚拟屏」（默认开）。
- 「登录时自动打开」：Sender 在控制面板，Receiver 在 App 菜单（退出全屏时可见），默认关，由用户自己打开。用 `SMAppService.mainApp`，App 移动位置后需要重新勾选。

实测：
- 替换 Sender 后，Air 上的 Receiver 约 2 秒自动连回，虚拟屏随连接自动创建。
- Air 实测断开/重连（用户确认成功）：断开 → 3 秒后虚拟屏移除 → 重新连上 → 虚拟屏重建、推流恢复。全程走 bridge0。

## 踩坑：本地网络权限弹窗被全屏窗口挡住

换成新版 Receiver 后，macOS 把它当成新 App，重新弹「查找本地网络上的设备」。旧设计一启动就全屏黑底，弹窗被挡住，用户看不到；没点允许之前，连接一直停在「正在连接」，没有任何报错（Air 日志里只有"连接 … 经由 bridge0"，之后什么都没有）。

修复：没连上之前不全屏；连接卡住时在窗口里显示原因，5 秒或 10 秒后自动重试。

另外从 Air 日志看到，Air 当前的缩放是 1710×1107 点（系统默认），不是 1440×932，所以画面会被系统再缩放一次。用户反馈"不糊"，先不处理。

## d. 4:4:4 色度实验

M4 Max 的硬件 HEVC 编码器支持 4:4:4，虽然 SDK 里没有对应的档位常量：输入 `444YpCbCr8BiPlanarVideoRange`、不设 `ProfileLevel`，输出就是 HEVC RExt（`chroma_format_idc=3`）。

本机回环对比（测试时另一路推流同时在跑，绝对值偏高，看相对差）：

| | 4:2:0 | 4:4:4 |
|---|---|---|
| 编码 | 13–16 ms | 17–18 ms |
| 解码 | 2.1 ms | 6.1–6.4 ms |
| 抓屏→显示 | 15–18 ms | 24–25 ms |
| 码率 | 28 Mbps | 90 Mbps |
| 彩色代码小字 PSNR（以 4:4:4 原图为基准） | 26.1 dB | 37.6 dB |

放大看：4:2:0 的彩色字发灰、偏淡，边缘发软；4:4:4 和原图几乎一样。黑白文字两者没有区别。

结论：做成开关（Sender 控制面板「4:4:4 色度」），**默认关**。打开后码率上限提到 300 Mbps。接收端连上后发 `hello` 报告自己能不能硬件解 4:4:4（现场编一小段码流实测），不支持就自动用 4:2:0。4:4:4 码流在接收端解成 BGRA 再显示。

注意：比较 4:2:0 画质时，"编码前"截图本身就是 4:2:0 抓的，色度损失在抓屏时已经发生，必须拿 4:4:4 原图当基准。

## c. 拍照测端到端延迟（准备好了，待用户拍照）

测试窗口改成堆叠布局：最上面是 44pt 毫秒时钟（60Hz 刷新），下面是各号字和彩色代码行。Sender 控制面板点「放测试窗口」，每块屏上都会出现一个，各个时钟走的是同一个时间。用手机同时拍下 Pro 主屏和 Air，两个时钟的差就是端到端延迟（含编码、网络、解码、Air 屏幕刷新）。
