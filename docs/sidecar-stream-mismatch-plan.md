# 随航画面错配：修复与验证方案

状态：手动随航重连及由软件控制的完整随航重连，分别已通过三轮同进程恢复、动态画面及输入确认。随航重新上线事件触发版已安装并开启，2026-10-26 首轮无需点击恢复入口的设备实验通过，结束后正常重新监测，没有自身重连循环。仅重建 AirDisplay 的路径失败；其他设备场景与无感兼容仍待验证，最终逐屏确认仍保留。

## 2026-10-25 已确认的现象

- 先创建 AirDisplay、后连接随航时，iPad 显示了 AirDisplay 的画面。
- CoreGraphics 报告三块独立且激活的显示器，没有镜像关系。窗口可以移入 iPad 对应的独立桌面，但 iPad 没有显示该窗口。
- 两块副屏的显示器标识不同；单独断开、重连随航没有恢复。
- 退出 Sender、断开随航，确认只剩内建屏，再先连接随航、后启动 Sender，用户确认恢复正常。
- 这次恢复同时改变了连接顺序并清空了虚拟显示器集合，尚不能把故障唯一归因于启动顺序。

## 外部证据与适用边界

- [BetterDisplay issue 4405](https://github.com/waydabber/BetterDisplay/issues/4405)：开发者复现多个虚拟屏重连后，ScreenCaptureKit 按正确 displayID 建流却返回另一块屏的内容；其绕过方法是断开所有虚拟屏后重新连接。
- [Apple Developer Forums 原始报告](https://developer.apple.com/forums/thread/786829)：同一开发者提交 FB17797423；Apple DTS 建议提交缺陷报告。这不是 Apple 对本项目根因或修复状态的确认。
- 与本次现象高度吻合，但尚无本项目中捕获源错配的程序化证明。正常的 displayID、屏幕数量或构建通过都不能证明画面来源正确。
- Sender 管理自身的 CGVirtualDisplay 和 SCStream，不能通过其 SCStream API 重置随航的画面流。不能承诺仅重启 Sender 抓屏就能修复 iPad。

## 修复范围

### 1. 增加可观察性和确定的生命周期

- 给虚拟屏实例、连接会话和抓屏启动分配进程内递增代号，记录创建、重配置、停止和恢复阶段。
- 显示器快照只记录进程内显示器 ID、类型、分辨率、坐标和镜像状态；不记录硬件序列号、UUID、设备个人名称、签名、地址或画面。
- 串行化抓屏停止和重新启动，等待停止完成；过期启动或旧流回调不能覆盖新会话。
- 虚拟屏延迟移除绑定到具体实例及断线代号。已取消的移除任务、旧实例的异步模式选择或 termination 回调不能影响新实例。
- 显示器配置持续变化时，不在超时后强行移除；保留显示器并显示原因，提供明确的手动操作入口。
- 这些修复用于消除本应用中的竞态，不把它们当作已证明的随航错配根因。

### 2. 在控制面板提供“恢复显示连接”流程

以用户点击为起点，不根据显示器数量或接入顺序宣称已经自动检测到画面错配。下列状态与互斥适用于菜单和控制面板的所有恢复入口；界面与代码一起完成，最后统一进行设备验收。

#### 2.1 先锁入口，再等待停止

1. **在任何异步等待之前进入统一的恢复状态，并递增操作代号，使此前所有启动、重启和自动移除任务失效。** 主线程上的虚拟屏和回环入口立即关闭；server 队列上的推流、重连和输入入口关闭并返回确认后，才能开始等待抓屏停止。
2. 所有入口都检查恢复状态和操作代号：Receiver 连接及 hello、设置变更重启、菜单与面板手动开启、测试启动参数、延迟启动、异步启动完成和显示器回调。不能只禁用按钮或只在 `displayProvider` 加判断。
3. 关闭输入接收并在同一串行执行域中释放已按下的键、鼠标键和修饰键，再等待网络抓屏与回环停止。此前已经进入注入回调的事件必须执行完，不能在释放按键之后继续注入旧事件。
4. 确认停止完成后才释放本应用虚拟屏。Receiver 连接可以保留，但恢复状态下不得创建虚拟屏、开始编码或推流；输入消息继续读取并丢弃，不能积压到恢复后重放。
5. 不以“对象已经释放”替代系统显示器查询。恢复流程必须实际观测到原 AirDisplay displayID 离线。

暂停期间输入始终禁用，贯穿停止、随航断开、重新接入、恢复建流以及待人工确认阶段。新连接不得重置这个禁用状态；设置中允许远程输入的偏好也不能覆盖恢复锁。

#### 2.2 第一阶段仅支持已知三屏环境

现有 `Displays.swift` 不能可靠区分随航和其他虚拟屏，第一阶段不凭名称、显示器数量或未验证的硬件字段声称完成了通用随航识别。

- 在开始恢复前取得有效基线：一块内建主屏、本应用持有的 AirDisplay，以及一块由用户在界面明确确认是 iPad 随航的副屏。若 AirDisplay 已被系统移除，允许从内建主屏 + 用户确认的 iPad 开始；这不算全量离线证据，后续仍必须实际观测到只剩内建屏。没有有效基线或出现其他显示器时，不自动推进这条路径。
- 用户按提示断开随航后，必须由**有效系统查询确认只剩同一块内建屏**，且本应用原 displayID 不在在线列表中。这是观察到的中间阶段，不能从“当前又有两块屏”反推此前已全部离线。
- 空列表、查询失败、枚举过程中数量变化、模式和交叉核验的实时几何信息均不可读、非正尺寸或状态不一致均为无效快照，不能算“全部离线”，也不能累计稳定时间。
- 观测到仅内建屏的稳定状态之后，用户重新连接随航；只允许出现“同一内建屏 + 一块新近上线、由用户确认是随航的副屏”。不要求新副屏的数值 ID 必须改变，系统可能复用 ID；重新接入的证据是中间离线阶段及其后的重新出现。
- 增加其他外接屏、其他虚拟屏或枚举结果不确定时，暂停并说明不符合本阶段实验条件，不擅自断开其他显示器。

#### 2.3 稳定性的可执行定义

- 使用单调时钟，每 250 ms 采样一次。快照签名按 displayID 排序，包含在线集合、内建/激活/主屏/镜像状态、显示模式和全局坐标。
- 必须至少有三次有效且相同的连续快照，且一致状态持续至少 1.5 秒；同时最近一次 CoreGraphics 显示器配置事件已经静默至少 1.5 秒。
- 任意快照变化、查询失败或新的配置事件均重置稳定窗口。在恢复开始时重置观测窗口，不能继承恢复前的静默时间。
- 1.5 秒是待设备实测验证的初始参数，不代表 macOS 已保证抓屏内容正确；上述检查只是允许推进恢复流程的条件。
- 操作停止和系统移除的单次等待设置明确上限（初始 10 秒），建流等候最多 60 秒；超时进入可见的暂停/失败状态，不跳过检查。确认原虚拟屏移除后，等待用户断开随航、重新接入和逐屏确认不设强制截止时间；超过 60 秒提示仍在等待，保留取消入口，继续有效快照检查，不因耗时自动进入暂停或恢复输入。
- 等待随航的界面明确说明：Air 暂停接收画面，会保留最后一帧且不能操作，请在 Pro 上完成连接步骤。避免把预期的暂停误认为 Receiver 死机。

#### 2.4 恢复建流与输入解锁

1. 只有在“仅内建屏”及“随航重新接入”两个稳定阶段均通过后，才允许当前恢复操作受控地创建一次 AirDisplay；普通启动入口仍保持关闭。
2. AirDisplay 被系统枚举为在线且模式稳定后，重新枚举可抓屏对象，建立当前代号的抓屏与编码会话。若 Receiver 已断线，明确显示等待 Receiver，不能视作恢复完成。
3. 接收到当前会话的有效完整帧并开始推流后，显示“推流已恢复，画面待确认”。帧、displayID 和帧率正常仍不能证明 iPad 显示正确。
4. 用户在三块实际屏幕上核对不同的动态标记后，从 Pro 上明确确认画面。仅此时才退出恢复状态；远程输入还需同时满足用户原有授权偏好、当前连接与当前推流有效。任何失败或再次断线均继续禁止输入。
5. 取消保持明确的暂停状态并使当前恢复任务失效，释放按键，不自动恢复推流或输入；“手动恢复 AirDisplay”是独立明确的操作，仅要求核对 Mac 和 Air，不标记随航错配已修复。

应用不结束系统进程、不修改显示器偏好文件。上述手动方式需要用户操作随航连接；后续已授权的软件重连方式及其验收结果见下方记录。

### 3. 减少后续触发机会

- 恢复流程期间，临时禁止接收端断线导致的虚拟屏删除和重建。
- 保留现有“Air 断开时移除虚拟屏”偏好，不静默改用户已选的行为。是否调整默认行为，依据恢复后的断线实测再决定。
- 后接入随航或睡眠唤醒时记录拓扑变化；仅凭接入事件不自动打断工作区，也不声称一定发生了错配。
- 自动修复 iPad 画面流仍为后续实验目标，不纳入未经实测即可交付的承诺。

## 实施顺序与设备验证关口

### A. 生命周期与最小恢复入口

- 先约定测试目录与命令，再实现统一恢复锁、操作代号、可等待的停止、远程输入隔离、有效拓扑快照和稳定性检查。
- 仅提供菜单中的实验入口、必要的阶段状态、确认/取消操作及本地脱敏日志；一般化的随航自动识别不在本次范围内；完整控制面板在设备实验前补齐。
- 最小入口也必须执行全部安全顺序和失败终态，不能通过“稍后补 UI”省略取消、超时、输入隔离或查询错误处理。
- 自动回归与 Sender 构建通过后，保留当前安装和正在运行的 App。设备试验使用新的构建，并按 `CLAUDE.md` 的固定签名与安装方式安排切换；不运行两个 Sender 干扰显示器状态。

### B. 完成恢复界面与本地交付

在设备实验之前完成控制面板引导：确认环境、等待停止、提示断开/重连随航、显示动态核对标记、逐屏确认、报告仍有错配、取消、失败重试和仅恢复 AirDisplay。所有界面操作使用同一个恢复状态，不能绕过输入锁或有效快照检查。断线重连后必须重新核对本次会话，不能沿用旧会话的确认。

同步文档，完成自动回归、构建、签名与界面布局验证，保留当前安装。交付标记为“代码完成，待设备验收”。两种启动顺序都无感正常仍是独立目标，不能由恢复流程或界面完成推导出来。

### C. 统一进行同进程恢复实测

完成全部恢复实现和本地验证后，先复现错配，再使用恢复入口，记录 Sender 的进程启动代号保持不变，并验证其抓屏停止、显示器实际移除、仅内建屏、随航重新接入以及恢复推流的顺序。

- 三块屏分别显示不同的屏幕标签、颜色与持续变化的计数标记；各屏的动态内容不同，不能只使用三屏相同的时钟。
- 在确实复现错误的前提下，连续完成至少三轮“故障 → 同进程恢复 → 人工逐屏确认”，记录每轮结果和触发顺序。不能把健康状态下的重建或一次成功计作可靠恢复。
- 另测恢复中 Receiver 重连、设置变更、手动开启、取消及查询失败，确认不会提前建流或注入输入。
- 如果不能复现、同进程路径失败、必须退出 Sender 才恢复，或无法验证真实画面，则保留证据并调整实现，不能因为界面已经完成就标记可靠恢复通过。

- `Sender/Sources/Displays.swift`：脱敏拓扑快照。
- `Sender/Sources/Loopback.swift`：可等待的停止，避免仍在抓屏时移除显示器。
- `Sender/Sources/InputInjector.swift`：目标屏无效时，键盘和鼠标输入均停止注入。
- `Sender/Sources/TestPattern.swift`：每屏不同的动态标记，避免把相同画面或残留帧误判为恢复。
- 恢复状态机与回归测试：实现前先在 `AGENTS.md` 约定新增测试位置及验证命令；不添加全局依赖。
- `CLAUDE.md` 与双语 README：实现验证后同步实际行为及限制，修正过时的“共存未验证”描述。

不改 Receiver 的线上协议、签名配置、系统设置或 CI/CD。不 push、不公开发布、不删除文件。

## 验证与验收

### 自动回归

- 恢复状态机：必须取得有效基线，观测到仅内建屏的稳定中间状态，以及随航重新出现的稳定状态后才恢复；顺序错误、超时、取消不得报告成功。
- 恢复开始即关闭所有启动入口：在停止完成之前注入重连、hello、设置变更、菜单开启和旧启动完成事件，均不得创建虚拟屏或新会话。
- 查询错误、空列表、枚举数量变化、模式无效、配置事件持续出现及额外显示器不得满足稳定条件；ID 被复用但确有离线中间状态时不能误拒绝。
- 使用可控单调时钟验证快照数量、1.5 秒持续时间和配置事件静默三个条件，不能依赖测试中的真实 sleep。
- 恢复过程中 Receiver 断线重连，不得创建虚拟屏；恢复后只启动一个会话。
- 输入隔离：先关接收并排空正在执行的注入，再补发抬起；恢复中后续输入必须丢弃，恢复待确认时也保持禁用。新连接、设置变化和过期任务不能提前解锁；人工确认后仍遵守用户输入偏好。
- 旧的抓屏启动完成、旧流报错、旧虚拟屏终止回调和待执行移除任务不得终止或覆盖新实例。
- 多次点击恢复、恢复中退出和无接收端时恢复有确定的终态。
- 使用可替换的显示器与流操作验证状态转移，不通过改系统设置来运行单元测试。

### 构建与静态验证

- 按 `CLAUDE.md` 生成工程并构建 Sender。
- 运行 `git diff --check`；检查文档链接、代码围栏和中英行为说明。
- 构建日志保持本地，用户可见结果和仓库文件不包含本机签名或硬件身份。

### 必须由真实设备完成的验证

| 场景 | 必须检查的内容 |
|---|---|
| 先随航、后 AirDisplay | 不同窗口或测试标记在三屏分别出现 |
| 先 AirDisplay、后随航 | 观察是否错配；若发生，应用内恢复流程可恢复 |
| 故障时只重启本应用抓屏 | 记录是否有效，不预设能修复随航 |
| 故障时执行最小恢复路径 | 同一 Sender 进程内连续至少三轮恢复；每轮逐屏核对不同动态标记 |
| 恢复中拔插 Air 连接 | 不提前重建虚拟屏，不重复建流 |
| 恢复时操作 Air 键鼠 | 释放原有按键；恢复中及画面待确认时的新输入不作用于 Pro |
| 休眠唤醒及随航重连 | 无旧任务误删新屏；若错配可恢复 |

第一阶段交付标准是“可靠恢复且不误报成功”。最终的无感兼容标准仍是两种启动顺序和重连均正常；只有真实设备验证通过后才能标记达到该标准。

## 恢复代码与界面本地验证（2026-10-25）

- `RecoveryPolicy.swift` 保存实际用于 App 的恢复状态与操作代号，`CaptureTransitions` 串行等待系统抓屏操作；`Tests/RecoveryTests.swift` 用可控时钟和挂起的假启动验证顺序，不操作实际设备。
- 菜单与控制面板均可打开恢复引导；开始前确认已知显示环境，完成前逐屏勾选动态标记。所有入口共用一个控制器，重连会清除旧流确认。以进程内随机会话标签记录同进程实验，不记录硬件 UUID 或序列号。
- 恢复流程依次等待停止、仅内建屏、随航重连、AirDisplay 稳定和当前会话关键帧写入连接。网络写入成功不代表 Receiver 已解码或 iPad 画面正确，最终确认仍必须由用户逐屏完成。
- 界面支持取消、失败重试、报告画面仍重复和仅恢复 AirDisplay；查询失败或 Receiver 换代会撤销旧的逐屏勾选。输入确认与网络消息处理串行，并核对确切流代号。
- “取消恢复”保留暂停；“仅恢复 AirDisplay”是独立操作，需要再次确认画面才能恢复输入，不证明完成过全量重置。
- 本轮本地验证如下。健康状态下的测试不得计入设备验收的三轮故障恢复。

| 检查 | 结果 | 证据边界 |

## 软件控制随航重连（已实施，当前设备三轮通过）

目标：用户不再进入系统设置断开、重连随航。优先实现一次点击完成重置；验证可靠后，再研究在已确认的随航连接事件后自动执行。自动化仍可能短暂中断副屏并移动窗口，不等同于修复 macOS 的抓屏实现。

### 新发现与证据边界

- [SidecarLauncher](https://github.com/Ocasio-J/SidecarLauncher) 提供连接和断开随航的命令，项目说明使用私有 API，并记录在 macOS Tahoe 26.5.1 从源码构建后可用；这不是本项目系统版本上的运行保证。
- 已阅读其 [main.swift](https://github.com/Ocasio-J/SidecarLauncher/blob/main/SidecarLauncher/main.swift)：通过 SidecarCore 的 SidecarDisplayManager 枚举设备并调用连接、断开方法。无需模拟点击系统设置。
- 本机只读运行时检查确认 SidecarCore 可加载，管理类及 devices、connectedDevices、connectToDevice:completion:、disconnectFromDevice:completion: 方法存在。未枚举个人设备信息，也未调用连接、断开方法。接口存在不代表实际调用会成功。
- BetterDisplay issue 4405 的自动重连绕过方法针对其管理的虚拟屏；不能把其效果直接外推到本项目对随航的控制。

### 实施与实验顺序

1. 先验证仅停止抓屏、移除并重建本应用虚拟屏，保持随航在线，能否恢复故障。此前等待全量离线时用户曾报告不再重复，但当时尚未重建 AirDisplay，不能据此认定该路径有效。
2. 若必须重连随航，增加隔离的 Sidecar 控制适配层，运行时检查私有方法可用性。针对用户首次明确选择的单台 iPad，保留本地目标引用；禁止断开无关显示器，日志不包含名称、设备标识或账户信息。
3. 沿用已验证的锁和状态机：关闭启动及输入、停止旧抓屏、移除 AirDisplay、请求断开目标随航、有效快照确认仅内建屏稳定、请求重新连接同一目标、确认随航重新上线并稳定、重建 AirDisplay、建流、逐屏确认。API 完成回调不代替系统离线、上线和稳定证据。
4. 连接失败、iPad 锁屏或不可达、接口不兼容、出现额外显示器或查询不确定时，终止自动尝试，进入可见暂停并提供现有手动恢复。设置明确调用超时和尝试上限；不修改安全设置，不结束系统服务，不安装外部命令行工具。
5. 核验扩展模式及显示布局是否保留。不能假定私有连接调用会保留原布局，不能只根据三屏数量、帧率或正常 displayID 自动报告成功。
6. 完成替身回归和 Sender 构建后，用真实故障至少三轮验证“无需手动随航重连”的路径；随后才增加事件触发，绑定连接代号、防重入和尝试上限，避免自身重建造成反复触发。没有可靠的像素来源证据时，不声称软件已自动识别所有画面错配。

用户已确认按此方案实施及安排设备实验。新增代码沿用 `Sender/Sources/` 与现有 `Tests/RecoveryTests.swift`，不添加依赖或修改签名配置；自动随航请求的顺序、取消、超时、重复和过期回调使用替身验证，测试不调用系统随航方法。实际连接控制只在 App 中用户选择自动恢复后执行，最终动态画面仍须人工确认。

实现保持三种明确方式：已验证的手动流程、保持随航在线的 AirDisplay 自身重建实验、自动随航重连实验。自动流程只针对开始时已连接且唯一的目标；取消或超时后的系统调用可能无法撤销，未返回的请求存在时禁止发起下一轮自动请求，晚到结果不得推进状态或解锁输入。事件自动触发须等设备实验通过后再实施。

### 随航重连事件自动触发的接入规则

用户要求将触发点从“发现重复后点击恢复”移至“iPad 断开后重新上线”。沿用此前已确认的实施顺序：第三轮自动恢复通过后接入事件触发；测试阶段保留逐屏画面及输入确认。

- 使用稳定的系统快照及 Sidecar 连接状态，限定已确认的内建主屏、当前 AirDisplay 和唯一随航目标。必须先观察真实随航离线，再观察其重新上线；移动显示排列、普通配置通知或应用启动时已有三屏不作为重连事件。
- 每个外部重连事件只消费一次。恢复开始即关闭所有启动入口和输入；自身发起的随航断开、连接、虚拟屏重建以及由此产生的配置事件全部抑制，不能重新触发恢复。
- 结束后用新的稳定显示快照重建基线；失败、取消、额外显示器、目标不确定、系统查询失败和超时均不能触发连续自动尝试。保留手动恢复入口，并显示失败原因。
- 触发意味着预防性重置连接，不意味着软件已检测到错误像素。仍可能短暂中断副屏或移动窗口；原故障是否不再可见、布局是否保留及是否可以减少最终确认，需单独验证，不能由已有两轮自动重连成功推导。
- 自动触发通过明确的应用开关启用，默认关闭；开启时限定当前已确认的三屏环境。跨进程不保存设备身份，每次运行从唯一已连接目标重新绑定；目标的 opaque 身份只在内存中比较，禁止写入偏好、日志或文档。目标不一致或读取失败时不自动控制设备。
- 初始三屏、随航离线和重新上线均使用有效连续快照与配置事件静默窗口，并交叉检查 Sidecar 的连接状态。恢复期间丢弃自身事件，恢复完成后只重新建立基线，不将已有三屏误认为新重连。控制器和事件状态机使用可控时钟回归验证。
